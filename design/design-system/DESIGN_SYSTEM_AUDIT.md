# Аудит интерфейсов и дизайн-системы Contour

Этот документ фиксирует исходное состояние проекта перед первым этапом новой Design
System и результат заложенной основы. Его задача — отделить уже работающую общую
основу от старых локальных стилей и не допустить опасной попытки переписать весь
интерфейс за один раз.

Аудит сделан по текущему рабочему дереву. Количественные значения ниже нужны как
ориентир масштаба, а не как требование механически заменить каждое найденное число.

## Короткий вывод

У Contour уже есть сильная визуальная основа: утверждённая палитра, светлая и тёмная
темы, Onest, общие отступы и радиусы, локальный набор иконок, production-логотипы и
проверки совпадения ассетов между сервисами. Всё это хранится в `design/`, который
уже объявлен мастер-источником.

До первой фазы единого машинного источника не было. Реальный продукт получал
значения из ручных CSS-файлов, а старый `design/brand/colors/tokens.json` описывал
только часть цветов и не управлял CSS. Admin, Mini App и Landing по-прежнему
содержат много локальных размеров, цветов и повторяющихся реализаций похожих
элементов.

Для новой основы выбран каталог `design/design-system/`. Канонические DTCG
JSON-токены находятся в `design/design-system/tokens/` и уже являются единственным
редактируемым источником. Генератор валидирует их и выпускает Web CSS, TypeScript,
resolved JSON, совместимые файлы из `design/brand/` и их точные service-копии.
Продукт пока подключает прежние пути, но их содержимое теперь generated.

Первая фаза создала мост между этими двумя состояниями без массовой перерисовки
продукта.

## Текущее состояние по продуктам

### Admin

Admin — серверные Flask/Jinja-страницы без frontend-фреймворка. Основной визуальный
слой сосредоточен в `services/admin/templates/base.html`, но отдельные страницы
также содержат собственные блоки CSS и inline-стили.

Что уже хорошо:

- подключены общие цвета, foundations, Onest и `product-theme.css`;
- есть адаптивная верхняя и нижняя навигация;
- страницы управления объявлениями, пользователями, откликами и платежами уже
  используют похожую композицию: заголовок, четыре показателя, переключатель,
  поиск, таблица и меню строки;
- иконки берутся из локального реестра, а не из CDN;
- основные состояния, focus и адаптив проверяются существующими тестами и
  браузерными сценариями.

Что мешает масштабированию:

- общий `base.html` одновременно является layout, библиотекой компонентов и местом
  для CSS конкретного дашборда;
- одинаковые паттерны имеют разные префиксы: `listings-*`, `users-*`,
  `responses-*`, `payments-*`, хотя их устройство почти одинаково;
- Button, tabs, search field, KPI card, badge, panel и row menu не имеют единого
  документированного API;
- старая палитра сначала объявляется литералами в шаблоне, а загруженный позже
  `product-theme.css` переопределяет только часть этих значений;
- в шаблонах остаются локальные размеры текста, отступы, высоты и inline-стили.

### Telegram Mini App

Mini App — отдельный Flask-сервис с большим vanilla JavaScript-файлом и единым
`style.css`. Он работает внутри Telegram WebView и поэтому дополнительно учитывает
цвета хоста, safe area, высоту viewport и особенности сенсорного focus.

Что уже хорошо:

- Telegram theme variables отделены от брендовых action/status tokens через
  `product-theme.css`;
- есть светлая и тёмная темы, reduced motion, focus-visible и touch-адаптация;
- общий локальный реестр контурных иконок используется в навигации и действиях;
- 3D-иллюстрации категорий, пустого состояния и экрана входа имеют мастер-копии в
  `design/` и проверяются тестами;
- карточки объявлений, полноэкранные сценарии, нижние шторки, snackbar и состояния
  загрузки уже образуют повторяемые продуктовые паттерны;
- видимые тексты проходят через локализацию RU/EN/KY/UZ.

Что мешает масштабированию:

- `.btn`, `.card`, `.wiz-input`, `.sheet`, profile controls и promotion controls
  повторяют близкие решения с разными локальными значениями;
- размеры текста включают множество промежуточных значений вроде `13.5px`,
  `14.5px`, `15.5px` и `16.5px`;
- focus ring, радиусы, тени и состояния кнопок повторяются в нескольких местах;
- часть product CSS обращается прямо к primitive tokens;
- иконки для новых действий можно указать строкой, даже если их нет в реестре.

### Landing

Landing состоит из трёх самостоятельных HTML-страниц. У каждой есть собственный
большой inline CSS-блок и исторически отдельная палитра. Поздний
`services/landing/static/brand/product-theme.css` связывает наиболее важные роли с
общими токенами Contour.

Что уже хорошо:

- все страницы используют локальный Onest и production-логотипы;
- базовые фон, текст, брендовые действия и focus уже можно переопределять через
  общую тему;
- страницы не требуют отдельной сборки и остаются простыми для независимого
  деплоя.

Что мешает масштабированию:

- три страницы имеют собственные Button, Card, Badge, header и layout-правила;
- внутри HTML остаются старые локальные палитры, тени и произвольные радиусы;
- breakpoints отличаются не только от Admin и Mini App, но и между самими
  лендингами;
- один из лендингов содержит inline SVG. Часть этих SVG является иллюстрацией, но
  сейчас технически не отделена от интерфейсных иконок;
- Landing пока не подключает общий runtime-реестр иконок.

### Telegram Bot

Bot не является web-интерфейсом: его UI состоит из сообщений Telegram, inline и
reply keyboard. Поэтому CSS-компоненты Admin и Mini App к нему неприменимы.

Что уже хорошо:

- пользовательские строки вынесены в локализацию RU/EN/KY/UZ;
- бот использует понятные Telegram-кнопки и обязательный продуктовый сценарий
  покрыт интеграционным тестом;
- production-аватар и приветственное изображение имеют мастеры в `design/`.

Что можно унифицировать позже:

- правила голоса интерфейса;
- названия и порядок типовых действий;
- паттерны подтверждения, ошибки, пустого состояния и возврата назад;
- правила использования брендовых изображений.

На первом этапе не нужно пытаться превратить Telegram keyboard в web Button или
подключать CSS-токены к Python-коду бота.

### Нативные приложения

Кода iOS и Android в репозитории сейчас нет. Первая фаза не создаёт SwiftUI или
Compose-компоненты, но канонический формат токенов не должен зависеть от Web, чтобы
такие генераторы можно было добавить позже.

release gate остановится на уже существующем интерфейсе ещё до появления первого
нового компонента.

## Существующие сильные стороны

### Мастер-ассеты и независимый деплой

`design/` уже является мастер-каталогом. Точные копии цветов, foundations,
типографики, WOFF2, логотипов, иконок, флагов и части иллюстраций лежат в нужных
сервисах. Это не случайное дублирование: каждый сервис отправляется отдельным
`git subtree`, а Docker build получает только его каталог.

Побайтовые тесты уже не давали этим копиям тихо разойтись. Новая сборка сохранила
эту модель: генератор выпускает все service-копии, а `--check` проверяет их
автоматически.

### Семантические цвета и темы

Текущий `tokens.css` уже разделяет primitive, semantic и часть component roles.
Есть роли фона, поверхностей, текста, границ, действий, статусов, focus, selection и
overlay для светлой и тёмной тем.

Новые файлы в `design/design-system/tokens/themes/` развивают эту модель и дают
обеим темам одинаковый контракт. Компонент должен обращаться, например, к
`color.action.primary`, а не к Forest 650.

### Foundations

Уже есть логичная сетка отступов с базовым шагом `4px`, общие control heights
`40/44/48px`, touch target `44px`, радиусы, border widths, motion и z-index.
Новые canonical tokens дополняют их типографикой, letter spacing, icon sizes,
breakpoints и aspect ratios.

### Доступность

Проект уже проверяет ключевой контраст, заметный focus, reduced motion, aria-роли
выбора языка, доступные имена кнопок и отсутствие зависимости статуса только от
цвета. Это хорошая база: доступность нужно перенести из отдельных проверок в
контракт каждого нового компонента.

### Проверенный визуальный процесс

Новые решения сначала фиксируются в `design/`, показываются владельцу и только
после выбора переносятся в сервисы. В `design/mockups/` и `design/design-qa.md`
сохранены источники, сравнения и найденные проблемы. Новая Design System должна
продолжать этот процесс, а не заменять его абстрактными компонентами без
визуального подтверждения.

## Дубли, конфликты и найденные дефекты

### Два конкурирующих источника токенов

До первой фазы документация говорила, что старые `tokens.css` и `tokens.json`
содержат одно ядро, хотя JSON описывал только часть цветов, а CSS вручную содержал
гораздо больше semantic и component roles. Не было генератора, проверки aliases,
циклов, совпадения тем и JSON-to-CSS parity.

Решение первой фазы реализовано: единственный canonical source находится в
`design/design-system/tokens/`, а CSS стал детерминированным результатом сборки.
Старые пути сохранены как compatibility outputs, чтобы не менять подключения всех
сервисов одним большим шагом.

### Конфликт правил геометрии и типографики

- `design/brand/foundations/README.md` и `--radius-card` задают карточке `12px`;
- `design/principles/design-principles.md` говорит о `20px` для карточек;
- Mini App фактически использует карточки с `16px` и отдельные поверхности с
  `20px`;
- правила дизайна называют `16px` минимальным основным текстом, а compact Admin
  широко использует `11–14px`.

Нельзя выбрать одно число и массово заменить остальные. Нужно разделить primitive
scale и semantic roles: компактная служебная поверхность, обычная карточка,
выразительная touch-карточка; body text, label и caption. До отдельного визуального
решения существующие размеры сохраняются как legacy.

### Обнаруженные неопределённые CSS variables

В Admin были найдены обращения к переменным, которых не было в подключённых стилях:

- `--danger` — используется для отрицательного тренда дашборда;
- `--radius-control` — используется в рассылке и её подтверждении;
- `--shadow-xs` — используется активными tabs на нескольких страницах;
- `--source-size` — использовался только в дочернем правиле диаграммы, при этом
  соответствующего элемента в разметке не было; мёртвое правило удалено.

Compatibility export первой фазы теперь определяет `--danger`,
`--radius-control` и `--shadow-xs` через canonical tokens. Для `--source-size`
системный токен намеренно не добавлялся: его единственный недостижимый потребитель
удалён.

Для использованного в Mini App `--motion-fast` добавлен compatibility alias на
canonical `motion.duration.fast`; существующий fallback по-прежнему безопасен.

Новый reference-слой проверяется на обращения к необъявленным `--rf-*`, а generator
ловит отсутствующие token aliases. Полную проверку всех legacy CSS variables нужно
добавлять как отдельный ratchet с исключениями для внешних `--tg-*` и действительно
динамических переменных.

### Исправленные отсутствующие иконки

Mini App вызывал через `iconLabel` три имени, которых не было среди 39 иконок
мастер-реестра:

- `sparkles` — действие «Продвигать»;
- `rocket` — поднятие объявления;
- `clock-3` — продление объявления.

Все три Lucide-совместимые иконки добавлены в мастер и service-копии. Static linter и
отдельный тест теперь собирают строковые вызовы из HTML/JS helpers и останавливают
проверку при неизвестном имени.

### Разные breakpoints

В продукте встречаются как минимум `350`, `520`, `560`, `620`, `640`, `800`,
`860`, `900`, `980`, `1000` и `1199.98px`. Не каждое media query должно быть
одинаковым, но сейчас нет различия между системным breakpoint и локальной точкой,
в которой конкретный контент перестаёт помещаться.

Canonical tokens уже предлагают общую шкалу `640/768/1024/1200/1440px`. Новые
компоненты должны использовать её. Старые content-specific breakpoints мигрируют
только после визуальной проверки каждого экрана.

### Дубли компонентов

Повторяются следующие семейства:

- primary, secondary, ghost и destructive buttons;
- icon-only buttons и close buttons;
- input/search field с label, clear и error;
- tabs/segmented control;
- Card/Panel/Surface;
- KPI/stat card;
- badge/chip/status;
- row menu/dropdown;
- modal, drawer и bottom sheet;
- empty, error, loading и toast/snackbar states;
- image placeholder, product thumbnail и avatar.

Это хорошие кандидаты для общей системы, но не все являются компонентами первой
фазы. KPI, таблицы, sheet и сложная навигация должны сначала опереться на базовые
Button, Text, Icon, Input и Surface/Card.

## Граница первой фазы

Первая фаза строит основу, но не меняет внешний вид всего продукта.

В неё входят:

1. Канонические framework-independent tokens в
   `design/design-system/tokens/`: primitives, semantic light/dark, typography,
   foundations и component aliases.
2. Детерминированная генерация Web CSS variables и compatibility aliases для
   существующих имён.
3. Автоматическая синхронизация generated CSS в Admin, Mini App и Landing с учётом
   независимого `git subtree`-деплоя.
4. Минимальные primitives: Text, Icon, Stack/Inline и Surface.
5. Фундаментальные компоненты: Button, Input/Field и Card. Вместе с Text и Icon это
   даёт запрошенные пять основных строительных элементов без создания сотен
   сущностей.
6. Статический каталог всех вариантов, размеров и состояний в `design/`, который
   можно открыть локально без отдельного production-фреймворка.
7. Документация правил расширения и короткая навигация для AI agents.
8. Static checks, component tests и подключение проверки к обязательному release
   gate.

В первую фазу не входит массовая замена `.btn`, `.card`, всех inputs или каждого
локального отступа. Новая система сначала доказывает, что умеет воспроизводить
текущие значения без визуального изменения.

## Что уже можно унифицировать

### Без изменения внешнего вида

- существующие color, spacing, radius, border, motion, z-index и control-height
  variables;
- Onest, font weights и базовая type scale;
- light/dark semantic roles;
- status colors и snackbar variants;
- focus ring и reduced-motion policy;
- icon sizes и API локального реестра;
- Button/Input/Card color roles, уже присутствующие в старом token CSS;
- byte-sync ассетов и токенов между master и сервисами.

### При следующем изменении соответствующего экрана

- четыре management page в Admin — через общие KPI, tabs, search и table patterns;
- Mini App `.btn`, wizard fields, listing card и image placeholder;
- повторяющиеся Landing buttons, badge и surface, если это не ломает авторскую
  композицию страницы;
- общие empty/loading/error states;
- media primitives для avatar, thumbnail и product image.

## Что нельзя мигрировать сейчас

- весь legacy CSS одной механической заменой;
- исторические файлы в `design/brand/concepts/`, `design/mockups/` и журнал Design
  QA;
- `design/prototypes/admin-overview/`: это изолированный React/Vite/Sites-прототип,
  а не production-библиотека Contour;
- Bootstrap Grid в Admin;
- внутренние цвета логотипов, иллюстраций, флагов и документированных canvas/SVG
  визуализаций;
- inline SVG-иллюстрацию Landing до отделения artwork от UI icons;
- Telegram `--tg-*`, safe-area `env()`, viewport units и другие platform contracts;
- проценты, `fr`, `auto`, `calc()` и data-driven размеры, которые не являются
  визуальными решениями;
- контент и keyboard Bot в Web components;
- пользовательские фотографии, тексты объявлений и данные из базы;
- географическую, платёжную или другую бизнес-логику под видом UI-рефакторинга.

## Карта миграции

| Сейчас | Первая фаза | После стабилизации |
|---|---|---|
| `design/brand/colors/tokens.css` редактируется вручную | Генерируется из `design/design-system/tokens/`, сохраняет старые CSS aliases | Product code постепенно переходит на новые semantic names |
| Foundations и typography существуют только как CSS | Их значения переносятся в canonical JSON, CSS становится output | Добавляются Swift/Kotlin exporters при появлении native-кода |
| Service-копии обновляются вручную | `build` обновляет master и все нужные копии, `check` ловит рассинхрон | Деплой принимает только проверенный generated output |
| `product-theme.css` связывает старые локальные имена | Остаётся platform/legacy adapter | Сокращается по мере исчезновения legacy variables, но Telegram adapter сохраняется |
| Admin `.btn`, `.panel`, inputs и management classes | Новые `rf-*` компоненты существуют рядом и проходят каталог/tests | Страницы мигрируют по одной при продуктовых изменениях |
| Mini App `.btn`, `.card`, wizard и sheet используют локальные значения | Button, Field, Card и media primitives доступны для новых участков | Сложные patterns мигрируют после отдельных визуальных задач |
| Landing имеет три локальных визуальных слоя | Общие токены и базовые компоненты доступны без смены композиции | Повторы убираются отдельно на каждой странице |
| Bot имеет Telegram-specific keyboard UI | Общие voice/action rules документированы | Появляется отдельный каталог Telegram patterns, не CSS-компоненты |
| Иконки выбираются строкой без полной проверки | Добавляются отсутствующие мастеры и static registry check | Все продукты используют один manifest и размерные tokens |
| Литеральные значения уже многочисленны | Вводится baseline: новые нарушения запрещены, старые не растут | Baseline уменьшается при каждой безопасной миграции |

## Подтверждённая очистка после первой миграции

После сверки Component Registry, текущей разметки и динамических class producers были
удалены только недостижимые остатки прежнего UI: неиспользуемый helper Catalog,
старые selectors каталога и skeleton Mini App, больше не создаваемые адаптеры темы,
неиспользуемые aliases Admin и Landing и selector декоративной полосы источника в
Admin. Удалённые правила уже были заменены текущими `catalog-*`/`rf-*` классами либо
не имели ни одного потребителя в текущем HTML/JS.

Generated Core UI, service-копии, Registry variants, иконки, шрифты, логотипы,
иллюстрации, исторические mockups и Design QA evidence при этой очистке не удалялись.
Тем самым legacy baseline уменьшился без изменения публичного Core API, поведения
или визуального результата: общий предел был снижен с `1656` до `1589`
зафиксированных сигналов. Следующий Field migration pass перевёл видимые поля Admin
и город/цену Mini App wizard на публичные Core primitives и дополнительно снизил
предел до `1506` после миграции Admin route filters, search actions, dashboard
selector и profile tabs на Core UI. Перевод плиток категорий Mini App с
Telegram/legacy aliases на композицию `Surface + Text` и semantic selected/focus
tokens дополнительно снизил предел до `1497`.

## Риски

### Визуальная регрессия из-за CSS cascade

Сейчас `product-theme.css` часто подключается после inline/page CSS и намеренно его
переопределяет. Изменение порядка файлов или объединение их в один bundle может
вернуть старые палитры либо изменить specificity. Generated output сначала должен
воспроизводить текущий результат, а не улучшать его.

### Рассинхрон независимых сервисов

Admin, Mini App и Landing не могут читать файлы из корня репозитория после subtree
deploy. Если генератор обновит только `design/`, production останется на старой
версии. `build` должен писать все копии, а `check` — проверять их побайтово.

### Кэш Telegram WebView и браузеров

Проект уже использует version query для CSS, JS, favicon и icons. При изменении
runtime output нужно одновременно обновлять cache version либо перейти на
детерминированный content hash. Иначе новый HTML может работать со старым CSS или
реестром иконок.

### Слишком строгий lint на старте

Немедленный запрет всех HEX, `font-size`, spacing и radius заблокирует текущий
продукт. Первая версия проверки должна быть строгой для новых файлов Design System и
работать как ratchet для legacy: число исключений может только уменьшаться.

### Ложная унификация

Не каждый похожий экран должен получить один гигантский компонент с десятками
флагов. Сначала используются composition и ограниченные `variant`, `size`, `state`.
Новый component появляется только для повторяемого поведения, а не для одной
визуальной разницы.

### Смешение темы продукта и темы Telegram

Mini App получает часть базовых цветов от Telegram. Нельзя записывать Telegram
variables в platform-independent token source. Они остаются WebView adapter поверх
semantic tokens и проверяются отдельно в обеих темах.

### Документационные противоречия

Правила радиусов и минимального текста уже расходятся с production. Если перенести
их в JSON без явного решения, конфликт станет автоматизированным. На первом этапе
нужно сохранить работающие значения, назвать разные semantic roles и вынести
неурегулированные решения на отдельное визуальное утверждение.

### Массовая миграция ломает обязательный продуктовый контур

Даже чисто визуальное изменение может нарушить создание, редактирование, отклик,
снятие и удаление объявления. После значимого изменения Design System обязателен
полный release gate с настоящими Flask, PostgreSQL и Chromium, без пропущенных
тестов.

## Критерий готовности первой фазы

Первая фаза считается готовой, когда:

- JSON в `design/design-system/tokens/` является единственным редактируемым
  источником токенов;
- aliases разрешаются без циклов и обе темы имеют одинаковый semantic contract;
- Web CSS генерируется детерминированно и service-копии совпадают;
- Button, Text, Icon, Input/Field и Surface/Card имеют документированные variants,
  sizes, states и accessibility contract;
- каталог показывает light/dark, keyboard focus, disabled, loading и error states;
- static checks находят stale token outputs, неверные aliases, неизвестные `--rf-*`
  в reference-компонентах, missing icons, direct primitive colors и новые
  произвольные значения;
- существующий legacy UI остаётся перечисленным и не объявляется мигрированным;
- текущие Design System tests и полный обязательный release gate проходят без
  пропусков.
