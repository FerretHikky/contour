Создаём Contour как единую систему

Foundations, компоненты и правила, которые помогают собирать узнаваемые интерфейсы быстрее и увереннее.

FoundationЦвет, типографика, размеры, сетка и другие основы интерфейса. PrimitivesБазовые элементы расположения, текста и доступности. ComponentsГотовые элементы интерфейса, сгруппированные по назначению и статусу. TemplatesГотовые сборки из системных компонентов для повторяемых сценариев.
Guidelines

Terminology

Canonical names нужны для одного общего языка. Synonyms используются только для discovery.

Часто путаютКак выбирать
TextField vs InputTextField — canonical editable field. Input deprecated и ведёт на TextField.
Dialog vs ModalDialog — canonical overlay contract. Modal deprecated.
BottomSheet vs DrawerBottomSheet адаптирован к нижнему краю Mini App; Drawer — боковая Web surface. Оба experimental.
Toast vs AlertToast transient и глобальный; Alert остаётся в контексте.
Badge vs ChipBadge сообщает metadata/status; Chip интерактивно выбирает compact option.
Spinner vs SkeletonSpinner — индикатор; Skeleton — заготовка геометрии загружаемого содержимого.
Divider vs SeparatorDivider — canonical primitive; Separator — discovery synonym.
ListItem vs RowListItem — structured reusable row; Row без contract остаётся layout/feature term.
SegmentedControl vs TabsSegmentedControl меняет local value; Tabs переключают content/navigation context.
Button vs LinkButton запускает action; Link ведёт на location.

Decision guide

Should this be Core?

Business reuse ещё не означает общий Design System contract.

  1. Есть existing component? Reuse его canonical API.
  2. Нет. Composition решает задачу? Соберите feature из Core.
  3. Нет. Нужен semantic variant? Предложите ограниченное расширение существующего contract.
  4. Нет. Generic need повторяется в unrelated product areas? Соберите evidence для Pattern/Core candidate.
  5. UI содержит Contour business meaning? Оставьте его feature component.

Guidelines

Do / Don’t

Короткие правила, которые останавливают visual debt до code review.

DoUse semantic tokens.Выбирайте роль, а не конкретный primitive color.
Don’tUse raw HEX.Raw color не выражает intent и не адаптируется к theme.
DoUse Button destructive variant.Переиспользуйте canonical action contract.
Don’tCreate RedButton.Цвет не является новым component meaning.
DoCompose Card + ListItem + Badge.Композиция остаётся прозрачной и проверяемой.
Don’tCreate another local Card.Local clone обходит Core contract и quality gates.
DoKeep ListingCard in feature layer.Product semantics остаётся рядом с business logic.
Don’tPromote after two similar screens.Core требует unrelated evidence и lifecycle review.
DoUse TextField.Search canonical name и existing variants.
Don’tCreate FormInput / CustomInput.Aliases не становятся параллельными components.

    Guidelines

    Accessibility

    Registry contracts и automated smoke checks снижают риск, но не доказывают полную compliance.

    • Semantics firstNative button, link, input, select и dialog сохраняют platform behavior.
    • KeyboardОсновной flow доступен Tab/Shift+Tab/Enter/Space/Escape без pointer.
    • Focus-visibleВсе interactive Core controls имеют явный semantic ring.
    • RelationshipsLabel, description, error, title и live feedback связаны через native/ARIA contracts.
    • TouchInteractive targets проверяются против minimum touch target.
    • Contrast and themesLight/Dark и forced colors проверяются отдельно; documentation не заменяет AT review.
